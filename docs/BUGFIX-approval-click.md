# Bug 复盘：点她的 √ / × 没反应

**现象**：审批牌在她头顶举起来了，点 √/× 好几次都没反应。

三个叠在一起的坑，**都不是猜的，逐个用工具验出来的**：

| # | 根因 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | 桥接脚本里 `/decision` 路由被一段**重复的空分支**挡在前面，客户端每次去领裁决连接都被无声关掉（空响应） | 原始 TCP 探针：`/ping` 200、`/state` 200、`/decision` **空响应** | 删掉重复分支；复测 `/decision` → **200** |
| 2 | 客户端领裁决用**全局单例解析器**（只有主路会设置），兜底退化成**全页面扫允许/拒绝按钮**，扫到的常是历史对话里旧的审批卡 | UI 自动化点她的 √：`decision.json` 写出来了，但日志里从来没有客户端领走的标记 | 改成 **id → 回调表**（`wnRegisterApproval` / `wnResolveApprovalById`）；兜底只认活审批条 + 排除历史消息里的按钮 |
| 3 | 点完她本地收牌，**300ms 后定时器又照读同一份 state 把牌子弹回来** | UI 自动化做「点前有牌 / 点后 5 秒还有牌」断言 | 记下**已裁决 id**（`decidedIds`），同一张牌永不回弹；状态过期后仍留 150 秒可点窗口 |

顺带补的可靠通道：宿主判定过门控后推来的 `cls=approval` 反应，现在会直接在她身上举牌并登记 resolver（`pet:real-ap`），不再依赖 DOM 里能不能扫到审批条。

## 复测证据（全链路，真实审批）

```
/decision 原始 socket      → HTTP/1.1 200 OK（修复前是空响应）
pet:live-ap / pet:real-ap  → 活审批条出现 / 宿主推来真审批，都给她举了牌
她的点击日志               → click yes id=appr-mur1v4m9
pet:desk-allo              → 客户端把裁决领走了
pet:real-allo              → resolver 成功点掉活审批条上的按钮（真审批被解决）
点击后 5 秒断言            → 牌子不再回弹
```

> 手法：给她的按钮做验证用的是 **Windows UI Automation**（`InvokePattern`）真按下去，再读 `decision.json` / 日志对账，不靠肉眼。
