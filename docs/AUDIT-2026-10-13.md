## 结论与范围

当前代码存在安装阻断、拒绝按钮失效、审批会话错绑、重装删除用户数据等问题，尚不适合直接作为稳定版本分发。审批链和安装器应优先修复，再处理桌宠交互与通知时序。

本次检查覆盖桌宠 WPF、HTTP 桥、插件宿主、客户端审批桥、启动恢复、安装脚本和表情包生成器。进行了 JavaScript/PowerShell 语法检查、无界面的 WPF 控件事件测试、提取实际客户端函数的隔离测试，以及使用临时目录和独立端口的真实 HTTP 测试。没有执行正式安装，也没有向真实 DSH 会话提交审批。测试材料保存在 `.diag/review/`；产品源码保持不变。

P1 表示阻断主流程、误操作或数据丢失；P2 表示明确的功能、时序、恢复或配置错误。代码可确认的问题与尚未进行的真实环境验证在下文分开说明。

## 优先修复的问题

### 1. P1：安装器存在语法错误，整个脚本无法执行

- 位置：[tools/install.ps1:56](E:/demo/桌面宠物/tools/install.ps1:56)。
- 代码中有 `$lan([char]0)`，这是无效的 PowerShell 表达式。
- 解析器报告 `Unexpected token '('` 等三个错误。PowerShell 会先解析整份脚本，因此错误虽然在末尾，前面的安装步骤也不会执行。
- 修复方向：移除损坏的表达式，并增加只解析、不安装的预检。该脚本还有中文且没有 UTF-8 BOM，交付目标是 PowerShell 5.1，修复时也应统一编码。

### 2. P1：“拒绝”按钮没有绑定处理器

- 位置：[whale-pet.ps1:467](E:/demo/桌面宠物/packages/desktop-pet/whale-pet.ps1:467)。
- 允许处理器与拒绝处理器都调用 `$btnYes.Add_Click(...)`，`$btnNo` 没有 Click 处理器。
- 无界面 WPF 事件测试：允许按钮写入 `allowed-once`；拒绝按钮写入次数为 **0**。
- 需要准确区分：当前正常初始化下，允许处理器会先清空 `pending`，而 `lastCardId` 没有被赋值，故第二个处理器通常不再写入。不能据此声称“允许必然变成拒绝”。确定的问题是拒绝按钮无效及事件绑定错误。
- 修复方向：将拒绝处理器绑定到 `$btnNo`，并分别验证两个按钮的最终裁决。

### 3. P1：后台会话的审批牌可以操作当前另一条会话

- 位置：[client.js:814](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:814)、[client.js:1268](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1268)。
- 宿主反应包含 `item.sessionId`，但 resolver 没有用它校验目标，而是调用 `wnClickLiveApproval()`，直接点击当前页面第一个活审批条。
- 隔离执行原函数：收到 **SESSION_A** 的审批反应后，将页面活审批设为 **SESSION_B**；裁决 A 的牌，实际点击的是 **B** 的允许按钮。
- 问题也出现在未知/过期 id 的兜底：[client.js:1299](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1299) 不校验 id，直接点击活审批；[client.js:1246](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1246) 还有全页面扫按钮的第二层兜底，没有排除历史卡片。
- 审批镜像只记录“有没有审批条”，不记录其 key：[client.js:1631](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1631)。审批 A 直接换成 B、期间未观测到空面板时，桌面的牌也不更新。
- 修复方向：裁决必须绑定真实 `sessionId + requestId`，身份不匹配时拒绝执行；不应根据按钮文案猜目标。

### 4. P1：重装会删除养成、记忆和位置数据

- 位置：[tools/install.ps1:42](E:/demo/桌面宠物/tools/install.ps1:42)。
- `robocopy $pet $petHome /MIR` 把源码目录镜像到运行目录，目标独有的运行 JSON 会被当作多余文件删除。
- 隔离目录验证：原有 `pet-stats.json`、`pet-memory.json`、`position.json`、`alive.json`、`hidden.json`、`decision.json` 全部消失；用户修改的 `lines.json` 被源版覆盖。
- 第 26 行的备份只保护 profile 清单，没有保护桌宠数据；第 43 行随后强杀进程，不能依赖进程再次补存。
- 这是被问题 1 暂时挡住的潜在数据丢失：一旦只修语法，重新安装就可能触发。
- 修复方向：程序资源与用户数据分目录；更新只覆盖程序文件，先备份并保留用户数据。

### 5. P1：普通通知、关键词和问候会撤掉待审批牌

- 位置：[client.js:821](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:821)、[client.js:1365](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1365)、[client.js:1385](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1385)。
- 这些非审批状态都传入 `approval:null`。HTTP 桥在 [whale-pet-http.ps1:98](E:/demo/桌面宠物/packages/desktop-pet/whale-pet-http.ps1:98) 整份重写状态；WPF 在 [whale-pet.ps1:739](E:/demo/桌面宠物/packages/desktop-pet/whale-pet.ps1:739) 立即撤牌。
- 触发例：会话 A 正等待审批，此时会话 C 完成，或加载页面后的问候触发，A 的牌消失，但审批 Promise 仍然待决。
- 隔离测试确认 completion 推送不包含 aid，后端会将 approval 写为 null。
- 修复方向：待审批队列应独立于表情/台词状态；日常演出不能清除审批。

### 6. P1：裁决被首次读取即删除，多窗口会抢走对方裁决

- 位置：[whale-pet-http.ps1:108](E:/demo/桌面宠物/packages/desktop-pet/whale-pet-http.ps1:108)、[client.js:1230](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/client.js:1230)。
- 每个客户端都轮询同一个 `/decision`，没有 client/session 筛选；服务端读文件后，在成功执行或回执之前就删除文件。
- 真实桥接测试：第一个请求得到完整裁决，第二个请求得到 `{}`。若先读到的是没有该 resolver 的窗口，原窗口永远领不到；结合问题 3，抢读窗口还可能误点自身审批。
- `OPTIONS /decision` 也会读取并删除裁决；真实测试已确认。这说明路由没有正确限制请求方法。
- 修复方向：按裁决所属客户端/请求领取，执行成功后确认；GET/OPTIONS 不应破坏未确认的数据。

### 7. P1：本地审批桥没有来源或身份校验

- 位置：[whale-pet-http.ps1:26](E:/demo/桌面宠物/packages/desktop-pet/whale-pet-http.ps1:26)、[whale-pet-http.ps1:79](E:/demo/桌面宠物/packages/desktop-pet/whale-pet-http.ps1:79)。
- 服务端反射任意 Origin，允许私有网络访问，且对写状态、读取裁决、唤醒均不验证调用方或令牌。
- 真实测试使用 `Origin: https://untrusted.example`：返回 `200 OK` 和相同的允许来源，伪造的 approval id 成功写入状态文件；裁决读取同样不受保护。
- 这确认了接口层缺少访问控制。具体浏览器网页能否发出请求，还受浏览器本地网络权限、CSP 等影响，本次没有验证浏览器穿透，更没有验证任意命令执行。
- 修复方向：限制可信来源、引入会话令牌，校验请求方法与审批身份。

## 通知与协议问题

### P2：前台 DSH 检测参数下标错一位

[notify.js:530](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:530) 传递 `[PROBE_EXE, DSH_EXE_NAME]`，C# Main 实际只收到一个参数 `args[0]`；[DshNotifyProbe.cs:44](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/activator/DshNotifyProbe.cs:44) 却要求 `args.Length > 1` 并读取 `args[1]`。结果 dshExe 为 null，present 位永远不设置，心跳过期时的宿主前台抑制失效。随包 exe 的 IL 也与该源码一致。修源码后还需要重新构建二进制。

### P2：关闭点击跳转，连桌宠反应接口也被关闭

[notify.js:1127](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:1127) 的 `cfg.clickToFocus` 分支一直包住 [notify.js:1220](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:1220) 的 REACT_PATH 注册。配置 `clickToFocus:false` 会同时取消 `/dsh-whale-notify/react`，导致客户端无法接收通知反应；点击功能与反应通道错误耦合。

### P2：延迟通知没有重新校验状态，也没有统一取消

- [notify.js:699](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:699) 只在入队前检查焦点，第 717 行限速等待后直接投递。用户已切回对应会话也仍可能弹提醒。
- [notify.js:740](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:740) 的 recheck 只检查焦点，不检查审批/提问是否已经解决，可能补发已过期的“等你点头”。
- [notify.js:986](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:986) 的 settle 和 recheck 定时器没有像 greetingTimer 一样接入 ctx.effect 清理，插件释放后仍可投递；重载时可能与新实例重叠。
- [notify.js:899](E:/demo/桌面宠物/packages/dsh-whale-notify/lib/notify.js:899) 的 blocked 兜底在入队前查 lastWaiting；另一条授权尚在队列时，它仍可能排入 question，最终对同一等待状态提醒两次。

上述路径经宿主隔离 mock 验证，未在真实 DSH 中触发通知。修复应在最终投递前复核焦点、请求存活状态和插件生命周期，而不仅在入队时检查。

### P2：中文 POST 正文会被读挂，原因是字节数与字符数混用

[whale-pet-http.ps1:69](E:/demo/桌面宠物/packages/desktop-pet/whale-pet-http.ps1:69) 将 HTTP Content-Length 当作 UTF-8 解码后的字符数，使用 StreamReader 继续等待不存在的字符。

真实服务测试：ASCII JSON POST 返回 200；同样包含中文“你好”的 JSON POST 等约 **5.04 秒**后连接关闭、响应为 **0 字节**，状态文件仍是前一份内容。这能解释至少一类过去的 POST 卡顿；没有证据将其全部归因于浏览器连接复用。当前客户端使用 GET，避开了这条主路径，但服务端声明支持的 POST 仍有 bug，并会在超时期间阻塞这个单线程服务处理其他请求。

## 根本原因与修复次序

主要问题集中在三个边界：审批身份没有贯穿宿主、客户端、文件和按钮；审批与日常表情共享一份覆盖式状态；运行数据、程序资源及进程健康判断没有分清。

建议依次处理：

1. 修复安装器解析错误、拒绝按钮和重装数据保护。
2. 将审批改为携带真实请求身份的独立队列，去掉跨会话 DOM 猜测，增加领取确认和来源校验。
3. 统一取消、超时、已处理和断线后的审批清理；日常状态不再清审批。
4. 接通 UI 心跳恢复，尊重主动隐藏，并统一安装目录传参。
5. 修复 WPF 交互、资源命名与通知时序，最后校正文档和默认配置。

必要的回归覆盖应集中在允许/拒绝、两个并发会话、两个客户端、取消/超时、审批期间普通通知、重装保留数据、UI 崩溃恢复，以及中文 HTTP 正文。这些场景比单纯“脚本能运行、窗口能出现”更能检验稳定性。
